# 새 게임 프로젝트 시작 문서 — 오름오름에서 가져가는 것 (2026-11-15)

새 프로젝트(스팀 용병 게임)의 지침이나 지식 문서로 넣어 쓴다. 담은 것: 게임 컨셉, 대답하는 방식, 세션을 나눠 일하는 방식, 그림체, 모델 만드는 방법. 오름오름의 게임 규칙(쓰레기·귤·오름)은 담지 않았다.

## 1. 게임 컨셉 (지금까지 정해진 것)

- 스팀용 게임. 용병 키우기
- 대규모 전투 속에서 약한 용병 한 명으로 살아가는 게임
- 용병을 직접 조작하며 전장을 뛰어다니는 액션 (키워서 내보내고 지켜보는 방식이 아님)
- 그림체는 오름오름과 같은 스타일 (5장)
- 개발은 AI 만으로 진행
- 엔진은 미정. Claude 의 추천은 Godot 4.7: 장면 파일이 텍스트라 AI 가 직접 읽고 쓸 수 있고, 화면 없이 명령줄로 실행·내보내기가 되어 자동 세션이 확인까지 할 수 있음
- 아직 안 정한 것: 엔진 확정, 한 판의 흐름(전투 전·중·후), 약한 용병이 재미있어지는 장치(살아남기·줄 서기·전리품·성장), 병사 수 규모, 싱글인지 멀티인지

## 2. 대답하는 방식

- 한글로, 짧게, 물어본 것만 답한다
- 모든 답변은 항목마다 번호(1. 2. 3. …)를 붙인다. 한 줄짜리 답변도 1번으로 시작한다. 번호는 답변마다 1번부터 새로 매긴다
- 한 번호에는 한 가지 내용만. 하위 항목은 번호 아래 글머리표로
- 사용자가 "2. …"처럼 번호로 답하면 바로 앞 답변의 그 번호 항목에 대한 답으로 읽는다. 번호 없이 새로 나온 요청은 새 요청으로 처리한다
- 사용자가 정해 줘야 할 것은 항목을 따로 떼어 번호만으로 답할 수 있게 적는다
- 안 물어본 부가 내용, 다음 단계 먼저 제안하기, 같은 말 반복을 하지 않는다. 의견은 사용자가 물었을 때 솔직하게 말한다
- 임의로 정한 값(수치·이름·범위)은 "제가 정한 값"이라고 밝히고, 확인하지 못한 것은 확인하지 못했다고 적는다
- GitHub 이슈 번호(#N)를 말할 때는 항상 그 이슈 링크를 건다
- 사용자 컴퓨터의 파일을 말할 때는 누르면 열리는 computer:// 링크로 준다
- 도구나 서비스에 관한 답은 공식 문서와 최신 웹 정보를 확인해 근거로 삼는다
- 이 게임들은 화면에 글자를 최대한 쓰지 않는다. 안내는 그림·아이콘·숫자로

## 3. 세션을 나눠 일하는 방식

### 3-1. 구조
- 기획 세션 하나: 사용자와 기획하고, 기획서와 이슈를 관리하고, 자동 실행을 돌리고, Tripo 로 모델을 만든다. 세션이 무거워지면 새 기획 세션으로 갈아탄다(결정은 그때그때 기획서와 이슈에 남겨 둔다)
- 이슈 세션: 이슈 하나에 새 세션 하나. 예약 작업이 자동으로 띄운다. 이슈 세션에는 새 일을 얹지 않는다
- 사용자는 개발 서버(또는 빌드)에서 직접 해 보고 기획 세션에 피드백을 준다. 기획 세션이 이슈로 정리해 실행 순서에 넣는다
- 이렇게 나누는 이유: 토큰을 먹는 것은 세션이 길어지며 쌓이는 맥락이다. 일을 이슈 단위로 끊으면 세션마다 맥락이 짧다

### 3-2. 이슈 쓰는 법
- 사안별로 잡는다(예: 이동, 적 한 종, 무기 한 종). 시안·수치·구현·확인을 한 이슈 안에서 끝낸다
- 본문만 읽고 시작할 수 있게 쓴다: 무엇을, 어떤 수치로, 어느 파일을, 무엇은 건드리지 않는지, 확인 방법
- 제목은 담백하게 할 일로. 본문은 "~해 주세요"로 끝나는 요청과 글머리표. 끝에 `기획 전체는 notes/spec.md, 작업 규칙은 notes/auto.md.` 한 줄
- 앞 이슈가 필요하면 본문에 "#N 다음에 해요"

### 3-3. 저장소에 두는 파일
- `notes/spec.md`: 기획서 사본(기준은 프로젝트 문서, 고치면 둘 다 고친다)
- `notes/queue.md`: 실행 순서 표. 열: 순서, 이슈, 모델(opus 또는 sonnet). 위에서부터, 닫힌 이슈는 건너뜀
- `notes/auto.md`: 자동 세션 규칙(아래)
- 큰 원본 모델은 별도 `assets` 브랜치에

### 3-4. 자동 세션 규칙 (`notes/auto.md` 내용)
```
시작
1. notes/queue.md 에서 위에서부터 처음으로 열려 있는 이슈 하나를 맡는다. 이슈 본문과 코멘트를 읽는다. 기획 전체는 notes/spec.md
2. 최신 dev 에서 work/<번호>-<짧은 이름> 브랜치를 만든다
3. 앞 이슈에서 만든 코드를 먼저 읽고 그 위에 얹는다

만들 때
- 이슈에 적힌 것만 한다. 무관한 코드는 고치지 않는다
- 새 3D 오브젝트는 지금 그림체에 맞춘 로우폴리 임시 모양으로 만든다
- 글자는 최소로, 아이콘 중심
- 수치는 한 파일(balance)에 모은다
- 예전 저장 데이터로 시작해도 오류가 없어야 한다

확인
- 빌드 통과, 실행 오류 없음을 확인한다. 새 기능은 값을 넣어 보며 동작을 확인한다

끝
1. 커밋하고 work/ 브랜치를 올린다
2. 확인이 통과했으면 dev 에 합쳐 올린다
3. 구조 문서에 새 모듈·결정 사항을 몇 줄 더한다
4. 이슈에 결과 코멘트(바꾼 것, 확인하는 방법, 임시로 둔 것·남은 점)를 달고 닫는다
5. queue 에서 다음 열린 이슈의 모델에 맞는 예약 작업을 fire_trigger 로 실행한다
- 확인이 통과하지 못하고 고칠 수 없으면: dev 에 합치지 않고, 이슈에 막힌 점을 코멘트로 남기고, 닫지 않고, 다음 작업도 실행하지 않는다
- release 는 건드리지 않는다. PR 은 만들지 않는다. 질문하지 않는다
```

### 3-5. 예약 작업 (기획 세션이 한 번 만들어 둔다)
- 둘을 만든다: "이슈 실행 (Opus)", "이슈 실행 (Sonnet)". 일정 없이 만들고 필요할 때 실행한다. 모델은 만든 뒤 각각 지정한다
- 프롬프트 틀:
```
<저장소> 에서 다음 이슈 하나를 수행한다. 사람이 지켜보지 않는 자동 실행이므로 질문하지 말고 끝까지 진행한다. 너는 "<opus|sonnet>" 예약 작업이다.
1. 저장소가 세션에 없으면 add_repo 로 붙이고 clone 한 뒤 dev 를 받는다.
2. notes/queue.md 에서 처음으로 열려 있는 이슈를 찾는다. 없으면 끝낸다. 모델 칸이 내 것이 아니면 다른 쪽 예약 작업(<ID>)을 fire_trigger 로 실행하고 끝낸다.
3. 내 것이면 notes/auto.md 를 그대로 따라 그 이슈 하나만 수행한다.
4. 성공해서 닫았으면 다음 열린 이슈의 모델에 맞는 예약 작업(<Opus ID> / <Sonnet ID>)을 실행한다.
5. 실패했으면 이슈에 코멘트를 남기고 다음 작업을 실행하지 않는다.
```
- 모델 고르기: 단순한 수정·제거·작은 기능은 Sonnet, 설계가 필요하거나 그림체·모델·UI 가 중요한 것은 Opus
- 기획 세션은 새 이슈를 등록하면 queue 에 줄을 더해 dev 에 올리고, 돌고 있는 것이 없으면 예약 작업을 실행한다. 그리고 1시간 뒤 자기에게 점검 알림을 예약해, 멈춘 곳이 있으면 다시 돌리고 다 끝나면 사용자에게 알린다

### 3-6. 사용자 승인이 필요한 것
- 실서버 배포("배포해줘")와 스팀 올리기
- 돈·크레딧이 드는 일의 첫 실행(Tripo 3D 생성은 한 번에 55크레딧), 파일 내려받기
- 시안을 골라야 하는 일: 시안을 여러 장 보여 주고 번호로 고르게 한다
- 그 밖의 이슈 등록·코멘트·닫기·dev 합치기는 승인 없이 진행한다

### 3-7. 브랜치
`work/<이슈 번호>-<이름>` → `dev`(개발 빌드 자동 게시) → `release`(사용자가 말할 때만)

## 4. 기획을 진행하는 방식

- Claude 가 초안을 내고 사용자가 항목별로 승인하거나 고친다
- 큰 기능은 한꺼번에 넣지 않고 첫 조각을 만들어 재미를 확인한 뒤 넓힌다(예: 적 한 종 + 무기 한 단계부터)
- 수치는 Claude 가 임의로 먼저 정하고, 사용자가 해 본 뒤 피드백으로 고친다
- 정해진 것은 바로 기획서와 이슈에 반영한다

## 5. 그림체 규칙

- 한 줄 요약: 낮은 폴리곤 + 툰 명암 + 따뜻한 햇빛과 푸른 그늘 + 후처리 없음
- 빛: 따뜻한 방향광(해) 하나 + 푸른 보랏빛 반구광(그늘). 블룸·색 보정 같은 후처리는 쓰지 않는다. 색 공간 변환 없이 적은 색이 그대로 화면에 나오게 한다
- 재질: 전부 툰 재질
  - 땅·풀은 부드러운 경계: 밝기 단계 120·150·215·255 를 선형으로 이은 램프
  - 나무·바위·캐릭터·동물은 또렷한 3단: 105·105·205·255 를 끊어 쓴 램프
- 시간대는 값 묶음으로 관리한다: 해 높이·해 색·세기, 반구광, 하늘 위·수평선 색, 구름 2색이 한 묶음. 오름오름은 낮(해 56°), 늦은 오후(23°, 기본), 노을(6.5°), 밤을 쓴다
- 땅 색 예: 풀 #62a64a·#86c257·#b9d264, 마른 풀 #d8b562, 붉은 흙 #a3553d, 길 #dcbb8c. 붓질 텍스처(512px, 큰 붓·중간·잔붓 3채널)로 섞어 손그림 느낌을 낸다
- 나무: 구 4~5개를 뭉친 수관(법선을 수관 중심 기준으로 둥글게, 아래쪽은 어둡게) + 층층 침엽수. 인스턴싱, 바람에 흔들림
- 풀: 플레이어 주변 칸에만 인스턴싱(데스크톱 약 5만, 모바일 약 1.7만 포기), 바람·밟으면 눕기, 땅 색을 그대로 받음
- 그림자: 방향광 그림자 1장이 플레이어를 따라다님(텍셀 단위로 스냅해 떨림 방지)
- 가림 처리: 나무·바위가 카메라와 캐릭터 사이에 오면 4×4 디더로 비치게 한다
- 캐릭터·동물: 아늑한 생활 게임풍 토이 스타일. 머리가 키의 약 40%, 매끈한 점토 질감, 얼굴에 인쇄한 듯 평평한 큰 세로 타원 눈, 코·입 없음, 볼터치 없음
- UI: 검은 유리(rgba(20,20,24,.5) + 흐림 12, 1px 흰 테두리 16%), 포인트 색 하나(귤색 #ff8a1f), 글자는 최소로 하고 아이콘 중심
- 레퍼런스: 웹 게임 Summer Afternoon(vlucendo)
- 다른 엔진으로 옮길 때: 툰 명암은 밝기 램프 텍스처를 읽는 셰이더로, 많은 것(나무·풀·병사)은 인스턴싱으로(Godot 는 MultiMeshInstance3D), 후처리와 톤 매핑은 끄고, 모델은 GLB 그대로

## 6. 모델 만드는 방법 (Tripo)

1. Tripo 스튜디오(studio.tripo3d.ai)의 이미지 생성(무료, Nano Banana)으로 시안을 4장씩 뽑는다
2. 사용자가 번호로 고른다. 고칠 점은 같은 화면의 이미지 편집으로 고친다(예: 볼터치 제거, T포즈로 바꾸기)
3. 고른 그림을 '3D 생성'으로 넘긴다(55크레딧, HD 모델). 결과는 약 190만 삼각형·60MB
4. GLB 로 내보내 받는다. 사용자 맥의 프로젝트 폴더에 정리하고, 원본은 저장소의 `assets` 브랜치에 둔다
5. Blender(`pip install bpy`)로 줄이고 텍스처를 굽는다. 오름오름 기준: 플레이어 캐릭터 9,000 삼각형, 멧돼지 1,500 삼각형·텍스처 512, 돌담 조각 가까이용 400·멀리용 60 삼각형. 병사 수백 명을 그릴 게임이면 병사는 더 낮게 잡는다
6. 뼈대는 직접 붙인다. 오름오름 캐릭터는 뼈 7개(엉덩이·가슴·머리·양팔·양다리) 가중치를 정점 위치로 계산했다

시안 프롬프트 틀(영어로 쓴다)
- 캐릭터·동물: `Original character, one animal only: <대상>, full body, three-quarter front view, standing, plain light gray background. Smooth rounded toy-like 3D render in a cozy life-sim game style, matte clay material. <몸 비율·특징>. Large flat vertical oval black eyes that look printed on the face. Soft studio lighting, no text.`
- 소품·구조물: `One <대상>, single isolated game asset, side three-quarter view. Stylized low-poly toy-like 3D render, chunky faceted shapes, matte <색>, no ground, plain light gray background, soft studio lighting, no text.`
- 이어 붙일 조각(담·울타리)은 `both ends cut flat so segments can be placed end to end` 를 넣는다

주의
- Tripo CLI·API 는 스튜디오와 크레딧이 따로라 쓰지 않는다. 사용자 맥의 크롬에 로그인된 스튜디오를 Claude 가 브라우저로 조작한다. 로그인이 풀려 있으면 로그인 창을 띄우고 사용자에게 요청한다
- 클라우드에서 도는 자동 세션은 Tripo 를 못 쓴다. 모델은 기획 세션에서 만들어 저장소에 올리고, 적용만 이슈로 넘긴다
- 60MB 원본은 작업 공간으로 올리다 실패한 적이 있다. 맥에서 gltf-transform 으로 먼저 줄여 올린다

## 7. 참고할 파일 (저장소 spaceHWI/oreumoreum, dev 브랜치)

- 그림체 구현: `src/namsongi.js`(지형·풀·나무·하늘·빛), `src/toon.js`(명암 램프)
- 캐릭터: `src/runner.js`, `src/runnermodel.js`, `model/bake.py`(줄이기·굽기), `model/extract.js`

## 8. 새 프로젝트 첫 메시지로 쓸 프롬프트

```
이 프로젝트는 스팀용 게임이다. 대규모 전투 속에서 약한 용병 한 명을 직접 조작하며 살아남고 조금씩 강해지는 게임.
개발은 AI 만으로 진행한다.
첨부한 "새 게임 프로젝트 시작 문서"의 대답하는 방식, 세션을 나눠 일하는 방식, 그림체, 모델 만드는 방법을 그대로 따른다.
이 세션은 기획 세션이다. 나와 기획을 정하고, 정해진 것은 GitHub 이슈로 만들어 이슈마다 새 세션이 자동으로 수행하게 한다.
먼저 정할 것: 엔진(추천은 Godot 4.7), 한 판의 흐름(전투 전·중·후), 약한 용병이 재미있어지는 장치.
```
