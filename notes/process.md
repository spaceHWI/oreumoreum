# 게임 제작 프로세스 (다음 게임에도 쓰는 틀)

오름오름을 만들며 다듬은 방식. 게임이 바뀌어도 그대로 쓸 수 있게 게임 내용이 아니라 **일하는 방법**만 적는다. 프로세스가 바뀌면 이 문서를 먼저 고친다(맨 아래 '바뀐 기록' 에 한 줄).

## 1. 역할
- **기획 세션**(사람과 대화하는 세션 하나): 기획·문서·이슈 등록·순서 정하기·검수·배포. 게임 코드는 고치지 않는다.
- **이슈 세션**(예약 작업으로 뜨는 자동 세션): 이슈 하나만 맡아 구현 → 확인 → dev 에 합치기 → 결과 코멘트 → 닫기. 사람에게 묻지 않는다. 규칙은 `notes/auto.md`.
- **오류 점검 세션**(2시간마다): 실서버 오류 묶음을 읽어 이슈로 만들고, 원인이 분명하면 고쳐 배포.
- 사람: 방향을 말하고, dev·실서버에서 직접 해 보고, 느낀 점을 짧게 말한다. 비밀 값 입력·가입·결제는 사람만.

## 2. 문서 (어디에 무엇을)
| 문서 | 내용 |
|---|---|
| `notes/spec.md` | 기획 전체와 날짜별 결정 한 줄 |
| `notes/journey.md` | 컨셉·줄거리·유저 저니(언제 무엇이 열리나)·시스템끼리 잇는 곳 |
| `notes/growth-loop.md` | 성장 수치 설계 |
| `notes/queue.md` | 이슈 실행 순서와 줄(나란히 도는 묶음) |
| `notes/auto.md` | 이슈 세션 규칙 |
| `notes/prototype-v1.md` | 코드 구조 |
| `notes/history.md` | 이슈별 메모 |
| `notes/process.md` | 이 문서 |
| `src/balance.js` | 모든 수치 한곳(임의값도 여기, 주석에 이슈 번호) |
세션 폴더는 사라지므로 저장소와 프로젝트 문서에 없는 것은 없는 것으로 본다.

## 3. 한 요청이 실서버에 나가기까지
1. **듣기**: 사람의 한 줄 요청. 뜻이 갈리면 하나만 묻고, 아니면 바로 진행한다.
2. **확인**: 코드에서 지금 상태를 먼저 본다(어디서 무엇이 어떻게 되는지, 원인 추정). 추정은 추정이라고 적는다.
3. **이슈**: 자급자족형 본문. 구성은 `요청 한 줄 → 지금(파일·줄·값) → 바꿀 것(번호, 임의값 표시) → 지킬 것(멀티·귤 벌이·성능·옛 저장) → 확인(돌릴 검사·코멘트에 적을 표)`. 끝에 기획서·규칙 문서 경로. 비슷한 요청은 같은 파일을 건드리는 이슈에 코멘트로 붙인다.
4. **순서**: `notes/queue.md` 에 넣는다. 서로 다른 파일을 건드리는 묶음은 줄로 나눠 **나란히** 돌린다. 앞 것이 뒤 것의 바탕이면 한 줄에 차례로. 맡으면 바로 '작업 시작' 코멘트와 브랜치를 올려 겹치지 않게 한다.
5. **구현**: 이슈 세션이 `work/<번호>-<이름>` 에서. 수치는 `balance.js`, 새 검사 도구는 `tools/` 에.
6. **확인**: 빌드, 오류(`err.js`), 보안(`sec.js`), 멀티(`online.js`), 귤 벌이(`econ.js`), 튜토리얼(`tutrun.js`), 싸움(`fight.js`), 성능(`perf.js`), 옛 저장. 재 본 값은 앞→뒤 표로 코멘트에.
7. **합치기**: dev 에 합치면 개발 서버에 자동 게시. 서버 코드는 이때 실서버 서버에도 나간다(그래서 옛 클라이언트와 맞아야 한다).
8. **검수·배포**: 기획 세션이 40분마다 dev 와 release 의 차이를 보고, 결과 코멘트의 검사가 통과면 버전·릴리스 노트(사용자 눈높이)를 올리고 빌드·오류·보안을 한 번 더 돌린 뒤 release 에 합친다. 3분 뒤 실서버 버전 파일로 확인한다. 실패한 검사가 있으면 배포하지 않고 알린다.
9. **알림**: 번호 붙여 짧게. 무엇이 나갔는지, 재 본 값, 임의로 정한 것, 남은 점. 이슈 번호에는 링크.
10. **돌아보기**: 실서버 오류 묶음, 받은 의견, 직접 해 본 느낌 → 다시 1.

## 4. 원칙 (겪고 나서 정한 것)
- **한 줄에 문장이 여럿인 곳에는 `//` 주석을 쓰지 않는다(`/* */` 만).** 줄 중간 `//` 가 뒤 문장을 통째로 지워, 오류 없이 튜토리얼이 멈춘 채 실서버에 50분 나갔다(2026-11-21 v0.37.0). 빌드 검사로 막는다.
- **실패한 검사를 '예전부터 실패' 라고 넘기지 않는다.** 그 자리에서 고치거나 이슈를 올린다. 배포 전에는 빌드·err·sec 에 더해 스모크(새 사용자로 튜토리얼 첫 단계가 시작되는지)를 돌리고, 배포 뒤 실서버에서도 한 번 본다.
- 배포 직전 `git pull --rebase` 로 딸려 온 이슈가 있으면 그 결과 코멘트를 읽고 스모크를 다시 돌린 뒤 내보낸다.
- **귤(재화)이 늘어나는 새 기능은 '서버가 그 몫을 아는가' 를 이슈 확인 항목에 꼭 넣는다.** 서버가 모르는 큰 보상은 서버 검증에 깎여 사용자 재화가 말없이 사라진다(2026-11-21 전리품 팔기 사고). 깎을 때는 사용자에게 알리고 기록을 남긴다.
- **나란히 할 수 있는 것은 늘 나란히 한다**(사용자 지시 2026-11-21). 새 이슈를 올릴 때 어느 줄에 넣을지부터 정하고, 서로 다른 파일을 건드리면 새 줄을 만들어 바로 따로 실행한다. 한 줄에 쌓아 두지 않는다. 급한 것은 줄과 상관없이 따로 실행한다.
- **검수와 배포는 기획 세션이 맡는다**(사용자 지시 2026-11-21): 개발 서버(dev)에 합쳐진 것을 기획 세션이 검수하고, 통과하면 묻지 않고 바로 실서버에 배포한 뒤 알린다.
- 임의로 정한 값은 '임의' 라고 밝히고 한곳(`balance.js`)에 둔다. 나중에 고치기 쉽다.
- 느낌이 아니라 **재서** 말한다. 난이도·귤 벌이·전송량·프레임은 도구로 재고 앞→뒤로 적는다.
- 서버와 클라이언트 수치가 함께 바뀌는 일은 배포를 미루지 않는다(서버가 먼저 나가므로). 돈이 되는 값(귤)은 서버가 정하고 클라이언트 말을 믿지 않는다.
- 새 시스템은 유저 저니의 '언제 열리나' 를 먼저 정하고 만든다. 화면에 말을 거는 것은 한 번에 하나(감독).
- 성장 수치를 건드리는 기능은 '5일 목표가 당겨지지 않는지' 를 확인 항목에 넣는다.
- 배포는 작게 자주. 하던 사람에게는 새 버전 알림으로 새로고침을 권한다.
- 자동 세션이 3시간 넘게 결과가 없으면 다시 실행한다(겹치기 방지 규칙이 있으므로 안전).
- 한 줄로 도는 줄 알았던 것이 실제로 어떻게 도는지는 규칙 문서와 예약 작업 글로 확인한다(가벼운 수정 줄이 큰 작업 뒤에 밀려 있던 일).
- 비밀 값은 저장소·이슈·문서에 적지 않는다. 공개 주소가 개인 정보를 내보내지 않게 한다.
- 실제 가게·사람 이름을 넣을 때는 로고·사진 없이 글자만, 정보는 공식·공개 자료에서 확인한다.

## 5. 새 게임을 시작할 때 (체크리스트)
1. 저장소 만들기: `work/* → dev(개발 서버 자동 게시) → release(실서버)` 브랜치와 게시 워크플로.
2. `notes/` 틀 복사: spec·journey·queue·auto·process, `balance.js` 한곳 규칙.
3. 검사 도구 뼈대부터: 빌드, 오류 잡기, 자동으로 한 판 돌리는 스크립트. 기능보다 먼저.
4. 예약 작업 둘(큰 작업·가벼운 수정)과 오류 점검 하나, 기획 세션의 40분 배포 점검.
5. 버전 파일·릴리스 노트·새 버전 알림·의견 보내기·오류 모으기를 첫 주에 넣는다.
6. 컨셉 한 줄과 유저 저니 표(첫 1시간·5일)를 먼저 쓰고, 그 표의 순서대로 이슈를 만든다.
7. 지침(`claude.md`)에 대답 방식·승인 없이 해도 되는 것·절대 하지 않는 것을 적는다.
